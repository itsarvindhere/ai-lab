In the last section, we talked about MCP Servers in detail. Well, let's talk about MCP Clients now.

MCP Clients are instantiated by the MCP Hosts to communicate with particular MCP Servers.

MCP Hosts are AI-powered applications that users interact with like a chatbot or an IDE. For example Claude Desktop, Claude Code, Cursor, VSCode etc.

So, it is important to understand that MCP Hosts do not directly communicate with the MCP servers. They use an MCP Client for that. So, an MCP Client sits between the MCP Host and MCP Server.

If Claude Desktop is the MCP Host, then the connection to a filesystem MCP Server is through an MCP Client.

It is also worth mentioning that each MCP Client handles one direct communication with one server. So, if the MCP Host connects to five MCP servers, it means there are five MCP Clients.

# PRIMITIVES

Just like how MCP Servers have three main types of primitives - Tools, Resources, and Prompts, the MCP Clients also provide several features to the MCP Server.

Sometimes the MCP server needs help from the client: workspace scope, user input, or an LLM call. That's where these primitives are useful.

There are three core client features that they provide.

## 1. ELICITATION

Elicitation lets the MCP Server ask the user for some specific information, providing a structured way for the MCP Servers to gather information on demand.

The method is -

    elicitation/create

Using this method, the server can initiate an elicitation. The MCP Client then uses this request and provides some sort of an Elicitation UI to the user, the user provides the requested information, the MCP Client sends back the information to the MCP Server and the server can now continue processing with this new information.

This is the whole flow.

For example, the user asked the AI app to book a hotel room.

When the MCP Server gets this request, the server might think -

    I can book the hotel, but I need the room type.

So, to get the room type, it can ask the user. To ask the user, it sends an 'elicitation/create' request to the MCP Client. The request might look like -

    {
        "jsonrpc": "2.0",
        "id": 3,
        "method": "elicitation/create",
        "params": {
            "message": "Choose a room type for your hotel booking.",
            "requestedSchema": {
                "type": "object",
                "properties": {
                    "roomType": {
                        "type": "string",
                        "enum": ["standard", "sea_view", "suite"]
                    }
                },
                "required": ["roomType"]
            }
        }
    }

So, the client takes this request, and the MCP Host can then show a dropdown to the user with options for different room types.

User chooses some room type and the MCP Client sends back the answer to the server. Maybe something like this is sent to the server -

    {
        "jsonrpc": "2.0",
        "id": 3,
        "result": {
            "action": "accept",
            "content": {
                "roomType": "sea_view"
            }
        }
    }

Note the same "id" 3 is present in the request that server sent to the client and the response that client sent to the server. This "id" is what lets client and server identify for what request a particular response is.

So, Elicitation is useful when the server should not guess.

For example -

    "What email address should I use?"
    "Which account should this invoice go under?"
    "Do you want economy or business class?"
    "What date range should I search?"

The client should make clear which server is asking and let the user accept, decline, or cancel.

But, Elicitation should not casually ask for secrets like passwords or API keys in a normal form. The newer MCP spec distinguishes safer form-based input from URL-based flows for sensitive authorization-style interactions.

## 2. ROOTS

With roots, MCP Clients tell the MCP Servers what workspace/filesystem areas are relevant. They are basically used to define filesystem boundaries. A root has a "uri" and a "name", something like -

    {
        "uri": "file:///Users/john/my-project",
        "name": "My Project"
    }

So, if an MCP Server asks for the list of roots, the MCP Client can send something like -

    {
        "roots": [
            {
                "uri": "file:///Users/arvind/my-project",
                "name": "My Project"
            }
        ]
    }

For example -

    User opens C:/projects/shop-app in an IDE.

    The IDE exposes that folder as a root.

    The filesystem MCP server knows to focus on that project.


But, why does this matter?

Without roots, the MCP Server cannot figure our what files it should look at. With roots, the MCP Client tells the server that these specific directories are relevant to your need.

Remember that roots are not hard security. They are just guidance. They communicate intended scope. A well-behaved server should respect them, but actual enforcement still needs sandboxing, permissions, or host-level controls.

If an MCP Client supports roots, it declares the same during initialization or handshake -

    {
        "capabilities": {
            "roots": {
                "listChanged": true
            }
        }
    }

If roots change, the client can send a notification -

    roots/list_changed

This tells the server that the roots have changed so with this information, server may request for the updated list of roots again using 

    roots/list

## 3. SAMPLING

This is an interesting one. Usually, we think that MCP Clients ask MCP Servers to do things. But with sampling, MCP Server can ask client -

    "Can you ask your model to think about this?"

The server can use this method to initiate a sampling request -

    sampling/createMessage

For example, a server may make a request to the MCP Client like this -

    {
        "jsonrpc": "2.0",
        "id": 2,
        "method": "sampling/createMessage",
        "params": {
            "messages": [
                {
                    "role": "user",
                    "content": {
                        "type": "text",
                        "text": "Analyze these 12 flight options and choose the best one."
                    }
                }
            ],
            "maxTokens": 1000
        }
    }

But why not let the MCP Server call an LLM directly? Well, with sampling, the MCP Server does not need to worry about having its own LLM Model API key. The MCP Client controls which model is used and the client controls the cost, permissions and safety. So, the MCP Server stays provider-neutral.

For example, let's say we have a Travel MCP Server. At one point, it may say to the MCP Client -

    I found 40 flights. Client, please ask the model to rank them based on the user's preferences.

So, The server provides the data. The client/model does the reasoning.

The sampling request that MCP Server sends to the client can also include model preferences like -

    {
        "modelPreferences": {
            hints: [{
                name: "claude-sonnet-4-20250514"
            }],
            "costPriority": 0.2,
            "speedPriority": 0.3,
            "intelligencePriority": 0.9
        }
    }

So, if an MCP Server prefers a specific model for some reasoning task, it can mention that in the request. Note that this is just a preference of the server. The client is still allowed to choose the actual model.

## AN EXAMPLE OF ALL THREE PRIMITIVES

Imagine a travel-planning MCP server.

    1. roots/list
    Server asks client: "What travel docs are in scope?"
    Client returns: file:///Users/john/trips/japan-2026

    2. sampling/createMessage
    Server asks client: "Analyze these flight options against the user's itinerary."
    Client runs the model and returns a recommendation.

    3. elicitation/create
    Server asks client: "Ask the user if they prefer cheaper flight or shorter layover."
    Client shows a choice to the user and returns the answer.

So these features make MCP more than "client calls server tools." They let MCP support richer loops:

    server needs context -> ask client roots
    server needs reasoning -> ask client sampling
    server needs human input -> ask client elicitation
