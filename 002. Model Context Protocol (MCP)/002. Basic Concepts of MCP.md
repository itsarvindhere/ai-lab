# PARTICIPANTS

Let's first understand what are the participants in the MCP. MCP follows a client-server architecture and there are basically three participants.

## 1. MCP HOST

This is the AI application which coordinates and manages one or more MCP Clients. For example Claude Code or Claude Desktop. The MCP Host establishes connection to one or more MCP servers by creating one MCP Client for each MCP sever.

The LLM is contained within the MCP Host and it is typically the user's interaction point, where the MCP host uses the LLM to process requests that may require external tools or data.

## 2. MCP CLIENT

This is the component that maintains a connection to an MCP server and obtains context from an MCP server for the MCP host to use.

It is contained within the MCP Host and it helps the LLM and MCP server communicate with each other. It translates the LLM requests for the MCP and converts MCP's replies for the LLM. It also finds and uses the available MCP servers.

## 3. MCP SERVER

This is the program that provides context to MCP Clients. This is an external service and it helps LLMs by connecting to external systems like database and web services.

For example, VSCode is an MCP Host. When VSCode establishes a connection to an MCP Server, then it instantiates an MCP Client object that maintains the connection to the MCP Server. When VSCode subsequently connects to another MCP server like local filesystem server, then VSCode runtime instantiates an additional MCP Client object for this connection.

MCP Server can execute locally or remotely. For example, when Claude Desktop launches the filesystem server, the server runs locally on the same machine as it uses the 'STDIO' transport. This is known as a 'Local' MCP Server.

Something like a 'Sentry MCP Server' uses a 'Streamable HTTP' transport and it is commonly known as a 'Remote' MCP Server.

# DATA LAYER

This is the part of the MCP that defines the ways developers can share context from MCP servers to MCP clients.

MCP uses JSON-RPC (Remote Procedure Call) 2.0 as its underlying RPC protocol. Client and servers send requests to each other and respond accordingly.

## JSON-RPC

JSON-RPC is a lightweight, stateless RPC protocol that uses JSON for data serialization. The standard request object contains -

    - jsonrpc - The version (2.0)
    - method - The procedure to be called
    - params - Optional Arguments
    - id - A unique client-defined identifier

The response contains 'result' if successful or 'error', along with the 'id' to match the request.

Let's say we want to call a method 'tools/list' with some parameters, a typical JSON-RPC request looks like -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "method": "tools/list",
        "params": {}
    }

And similarly, we may get a response -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "result": {
            "tools": []
        }
    }

## WHY JSON-RPC OVER SOMETHING LIKE REST?

MCP needs both sides to send structured messages back and forth and JSON-RPC fits that shape well because it is 'Transport-Independent', 'Bi-directional', and 'method-oriented'.

It is transport-independent as it can run over stdio, HTTP, Websockets, Local processes and other streams.

This is why it is used over something like REST.

This matters because many MCP servers are launched locally as subprocesses. For example, an AI app can start a 'filesystem MCP server' and talk to it over standard input/output (stdio). REST does not fit that local process model as naturally.

It is bidirectional. REST is mostly client to server. Client sends an HTTP request, server sends an HTTP response. MCP needs more than that. The server may send notifications, progress updates, logging messages, resource change events or requests back to the client. JSON-RPC supports this message-style communications more naturally.

MCP has operations like 'initialize', 'tools/list', 'tools/call' etc and those map cleanly to JSON-RPC methods. REST would model these as URLs and HTTP verbs, such as 'GET /tools', 'POST /tools/call' etc. That an work, but it becomes less elegant when the protocol is really about invoking named capabilities rather than manipulating web resources.

JSON-RPC has 'id' so multiple requests can be in flight and responses can arrive later. This is useful for agents doing multiple operations or long-running tool calls.

So, MCP is less about "resources over HTTP" and more about "two programs exchanging protocol messages." REST wouldn't be the best choice for MCP because REST assumes HTTP as the main transport, it is mostly client-initiated, it does not naturally support server-to-client requests over plain HTTP, local stdio-based communication would need a different design etc.

REST is like ordering from a menu through a waiter: request, response, request, response.

JSON-RPC is like having a structured walkie-talkie channel where either side can send typed messages, some expecting replies and some just announcing events.

So, In MCP, that second model is a better fit.

# TRANSPORT LAYER

The transport layer manages the communication channels and the authentication between clients and servers. It supports two transport mechanisms -

## 1. STDIO TRANSPORT

Uses standard Input/Output streams for direct process communication between local processes on the same machine.

## 2. STREAMABLE HTTP TRANSPORT

Streamable HTTP was introduced in the MCP that allows AI Clients and servers to communicate using a single endpoint for both standard request-response and real-time streaming.

Before this, HTTP + SSE was used but it has been officially deprecated in favor of Streamable HTTP.

# PRIMITIVES

This is the most important MCP concept. The primitives define what clients and server can offer each other.

MCP defines three core primitives that can be exposed by the servers -

## 1. TOOLS

These are executable functions that AI applications can invoke to perform actions e.g. file operations or API calls or database queries.

## 2. RESOURCES

Data sources that provide contextual information to the AI applications like file contents, database records, API responses etc.

## 3. PROMPTS

Reusable templates that help structure interactions with language models. These are user-controlled.

Tools do things. Resources provide information. Prompts structure conversation.

As a concrete example, consider an MCP server that provides context about a database. It can expose tools for querying the database, a resource that contains the schema of the database, and a prompt that includes few-shot examples for interacting with the tools.

For example, let's say we have a GitHub MCP Server. It can have -

    Tool: create_issue, search_repositories, comment_on_pr

    Resource: repo://my-app/README.md, repo://my-app/issues/123

    Prompt: review_pull_request, write_release_notes

The server primitives are the ones where the server exposes them so the client can use them.

Then, we also have primitives that 'clients' can expose. So now, the direction flips. These are the capabilities that servers can request from the client.

There are three main client-side primitives.

## 1. SAMPLING

It lets an MCP server ask the client's LLM to generate/analyze something.

This is useful when the MCP Server authors want to access a language model but want to stay model-independent and not include a language model SDK in their MCP Server.

They can use the 'sampling/createMessage' method to request a language model completion from client's AI application.

Example: a travel MCP server has a 'find_best_flight' tool. The server can fetch 40 flight options, but deciding “best” may require reasoning. Instead of embedding its own LLM, it asks the client. This is useful because the server stays model-independent. It does not need OpenAI, Anthropic, or local model SDKs. The client controls model access, permissions, cost, and user approval.

## 2. ELICITATION

It lets an MCP server ask the user for missing structural information. This is useful when server authors want to get more information from the user, or ask for confirmation of an action.

They can use the 'elicitation/create' method to request additional information from the user.

Example: a booking server is about to reserve a hotel, but it needs confirmation. So instead of the server guessing or failing, it can say: 'I need a human decision here.'

## 3. LOGGING

This enables MCP Servers to send log messages to the clients for debugging and monitoring. A server might log -

    {
        "level": "info",
        "message": "Indexed 128 files"
    }

This helps clients show status, diagnostics or developer logs.

So, server primitives are about what 'server provides to the AI application.'

Client primitives are about what 'client provides back to the server.'

This is one reason MCP is not just a normal REST API. The server is not only passively receiving requests. It can also ask the client for model calls, user input, and logging support.

# NOTIFICATIONS

In MCP, notifications are one-way messages.

They are sent from client to server or server to client, but they do not expect a response.

A normal MCP request has an 'id' -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "method": "tools/list",
        "params": {}
    }

Because it has an id, the receiver must eventually reply with a matching response.

A notification has no 'id' -

    {
        "jsonrpc": "2.0",
        "method": "notifications/tools/list_changed"
    }

So, no 'id' means - 'I am telling you something happened. You do not need to reply.'

For example, when a server’s available tools change—such as when new functionality becomes available or existing tools are modified—the server can send tool update notifications to inform connected clients about these changes.

Notifications are sent as JSON-RPC 2.0 notification messages (without expecting a response) and enable MCP servers to provide real-time updates to connected clients.
