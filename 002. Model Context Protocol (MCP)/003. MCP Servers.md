An MCP server is a program that gives an AI app controlled access to some external capability or context.

An MCP Server might wrap your filesystem or a database or GitHub or Slack or any external application.

It is important to understand that MCP Servers do not usually talk to the LLM. Instead, they talk to an 'MCP Client' and the client is inside an 'MCP Host'. Claude Desktop, VSCode, Codex etc are examples of 'MCP Hosts'.

Each MCP server is specialized and it does not need to know about every tool in the world.

An MCP server can be 'local' or 'remote'. A local MCP server might be launched by the MCP Host as a subprocess. For example the AI app starts a filesystem MCP server on your machine. The communication often happens over 'stdio' or 'standard input/output'.

A remote MCP server runs somewhere else. For example, an AI app connects to a remote GitHub MCP server over HTTP. Modern MCP servers commonly use Streamable HTTP for remote servers.

Remember, when we say 'MCP Server', the 'server'  does not necessarily mean a 'web server'. It just means a program that implements the MCP server side of the protocol.

# MCP SERVER LIFECYCLE

When a client connects to a server, they do a handshake.

## 1. Client sends 'initialize' request

The 'initialize' request is something like -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "method": "initialize",
        "params": {
            "protocolVersion": "2025-06-18",
            "capabilities": {
                "elicitation": {}
            },
            "clientInfo": {
                "name": "example-client",
                "version": "1.0.0"
            }
        }
    }

## 2. Server replies with protocol version, capabilities, server info

The server declares what is supports during initialization. This is capability negotiation. So, the MCP Client should not assume that every MCP Server supports every feature -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "result": {
            "protocolVersion": "2025-06-18",
            "capabilities": {
                "tools": {
                    "listChanged": true
                },
                "resources": {}
            },
            "serverInfo": {
                "name": "example-server",
                "version": "1.0.0"
            }
        }
    }

The reason why 'protocolVersion' field is present in request and response is to ensure that both client and server are using compatible protocol versions.

The 'capabilities' object allows each party to declare what features they support.

The 'clientInfo' and 'serverInfo' objects provide identification and versioning information for debugging and compatibility purposes.

## 3. Once handshake is successful, normal operation begins

The client can use the 'tools/list' request to discover the available tools and then use 'tools/call' request to execute a specific tool.

# PRIMITIVES

In the previous section, we learnt that MCP Servers expose three main primitives. Let's talk about them in detail.

## TOOLS

Tools are the 'functions' that the LLM can call. It depends on the user's prompts whether a tool is called or not. For example, a user might ask -

    How many users signed up yesterday?

In this case, the model will decide that it needs database access. There might be a database MCP server which exposes a 'query_database' tool. So, the MCP client asks the user for approval (depending on the app) and then sends a 'tools/call' request to the MCP server. The server then runs the query and returns the result. This result is what the AI app uses to answer your query.

There are two main operations -

    1. tools/list - Discover available tools. This returns an array of tool definitions with schemas.

    2. tools/call - Execute a specific tool. This returns the tool execution result.

For example, first the client calls -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "method": "tools/list",
        "params": {}
    }

Then, the server responds with the available tools -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "result": {
            "tools": [
            {
                "name": "query_database",
                "description": "Run a read-only SQL query",
                "inputSchema": {
                    "type": "object",
                    "properties": {
                        "sql": {
                            "type": "string",
                            "description": "SQL query to execute"
                        }
                    },
                    "required": ["sql"]
                }
            }
            ]
        }
    }

So, this tells the client that there is a tool named 'query_database' which requires one argument named 'sql'.

So, if a user asks how many users signed up yesterday, a the LLM might decide it needs the database so it prepares the arguments -

    
    {
        "sql": "SELECT COUNT(*) FROM users WHERE created_at >= '2026-05-13' AND created_at < '2026-05-14';"
    }

Note that the model is not directly executing this SQL query. Now, the MCP Client calls the tool using the 'tools/call' method -

    {
        "jsonrpc": "2.0",
        "id": 2,
        "method": "tools/call",
        "params": {
            "name": "query_database",
            "arguments": {
                "sql": "SELECT COUNT(*) FROM users WHERE created_at >= '2026-05-13' AND created_at < '2026-05-14';"
            }
        }
    }

Notice the structure. The 'name' chooses the tool and 'arguments' must match the tool's 'inputSchema.'

Next, the MCP server receives the call and it might validate the arguments first, then check whether the query is allowed, open database connection, run query, format result, and return the result to the MCP Client.

Ideally, for safety, a real query_database tool might only allow SELECT, not INSERT, UPDATE, or DROP.

Next up, the MCP Server returns the result. Something like -

    {
    "jsonrpc": "2.0",
        "id": 2,
        "result": {
            "content": [
                {
                    "type": "text",
                    "text": "count\n42"
                }
            ]
        }
    }

So, the 'result' contains the actual result of the tool call. And based on this, the model can answer the user like -

    42 users signed up yesterday.

## RESOURCES

In MCP Servers, 'resources' are readable context exposed by an MCP Server.

So, if tools are for 'doing actions', resources are for 'providing information'.

Each resource has a unique URI and declares its MIME type for appropriate content handling. For example, an MCP server might expose resources like -

    file:///project/README.md
    file:///project/package.json
    postgres://schema/public
    github://repo/acme/app/pull/123
    docs://payments-api/authentication
    logs://production/api-errors/today

A resource usually represents some piece of data the model may need as context.

Let's say we have a database MCP Server. It might expose -

    postgres://schema/public
    postgres://table/users/schema
    postgres://table/orders/schema

These are resources that the MCP Client can read to understand database structure.

Resources are of two types in MCP -

    1. Direct Resources - They are fixed URIs that point to a specific data. Use direct resources when the server knows the available items ahead of time or can enumerate them reasonably.

    file:///project/README.md
    file:///project/package.json
    postgres://schema/public
    docs://api/authentication

    2. Resource Templates - They are dynamic URIs with parameters for flexible queries.

    github://repo/{owner}/{repo}/issue/{number}

    This says - 'I can read GitHub issues if you provide owner, repo, and issue number.'


In MCP there are four operations related to resources -

    1. resources/list - List all the available resources. Returns an array.

    2. resources/read - Retrieve the contents of the resource. Returns the resource data with metadata.

    3. resources/subscribe - Listen to resource changes. Returns a subscription confirmation.

    4. resources/templates/list - Retrieve resource templates. Returns an array.

So, if an MCP Client makes a 'resources/list' request, it might receive -

    {
        "resources": [
            {
                "uri": "file:///project/README.md",
                "name": "README",
                "description": "Project overview",
                "mimeType": "text/markdown"
            },
            {
                "uri": "postgres://schema/public",
                "name": "Public schema",
                "mimeType": "application/json"
            }
        ]
    }

Let's say we want to read the 'README.md' resource's content. MCP Client can then request -

    {
        "method": "resources/read",
        "params": {
            "uri": "file:///project/README.md"
        }
    }

Similarly, to get resource templates, the user can make a 'resources/templates/list' request that may return -

    {
        "resourceTemplates": [
            {
                "uriTemplate": "github://repo/{owner}/{repo}/issue/{number}",
                "name": "GitHub issue",
                "description": "Read a GitHub issue by repository and issue number",
                "mimeType": "text/markdown"
            }
        ]
    }

And to read the content, the MCP Client can make the 'resources/read' request -

    {
        "method": "resources/read",
        "params": {
            "uri": "github://repo/vercel/next.js/issue/12345"
        }
    }

But, why resource templates even exist?

Imagine a GitHub MCP server.

It cannot list every possible issue from every repo:

    github://repo/{owner}/{repo}/issue/{number}

That space is huge.

Same with -

    users://{userId}/profile
    orders://{orderId}
    docs://{product}/{version}/{page}

Templates let the server say:

    "I support this family of resources. Give me the right URI and I can read it."

## PROMPTS

Finally, we have 'Prompts' that are exposed by the MCP Servers. They are like named workflows the user or app can invoke.

So, if a 'tool' is used to do an action and a 'resource' is used to read context, then a 'prompt' is used to prepare a conversion or task.

A prompt does not execute code by itself. It returns messages that the client can feed into the model.

So, a GitHub MCP server might expose these prompts -

    review_pull_request
    summarize_issue
    write_release_notes

A database server might expose:

    explain_schema
    generate_safe_query
    debug_slow_query

So instead of the user writing a long instruction every time, the server provides a reusable prompt.

There are two operations -

    1. prompts/list - Discover available prompts. Returns an array of prompts.

    2. prompts/get - Retrieve prompt details. Get full prompt definition with arguments.

So, an MCP Client might make a request as -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "method": "prompts/list",
        "params": {}
    }

In this case, server might respond as -

    {
        "jsonrpc": "2.0",
        "id": 1,
        "result": {
            "prompts": [
                {
                    "name": "review_pull_request",
                    "description": "Review a pull request for bugs and risks",
                    "arguments": [
                        {
                            "name": "pr_url",
                            "description": "URL of the pull request",
                            "required": true
                        }
                    ]
                }
            ]
        }
    }

This tells the client -

    I have a prompt called 'review_pull_request' which needs a 'pr_url'.

So, the MCP Client might want to get more details of this prompt so, it can make a 'prompts/get' request -

    {
        "jsonrpc": "2.0",
        "id": 2,
        "method": "prompts/get",
        "params": {
            "name": "review_pull_request",
            "arguments": {
                "pr_url": "https://github.com/acme/app/pull/42"
            }
        }
    }

The server then returns -

    {
        "jsonrpc": "2.0",
        "id": 2,
        "result": {
            "description": "Review a pull request for bugs and risks",
            "messages": [
            {
                "role": "user",
                "content": {
                    "type": "text",
                    "text": "Review this pull request for correctness, regressions, security risks, and missing tests: https://github.com/acme/app/pull/42"
                }
            }
            ]
        }
    }

The client can then insert that into the chat or send it to the model.

You might confuse prompts with tools. But, prompts are not the same as tools. If you call a tool using the 'tools/call' request, then the MCP Server will perform an action and return the result.

But, if you call 'prompts/get', the server just returns a prepared message or a message sequence and that is it.

Prompts can guide the model to use context.

So, a database MCP Server might expose a prompt named -

    explain_table

In this case, the returned prompt might say -

    Using the schema resource for this table, explain its columns and relationships.

Prompts are user-controlled so they require explicit invocation. The model usually does not randomly invoke prompts in the same way it may decide to use tools.

The reason prompts exist is because MCP Servers know the best way to interact with their own domain. A GitHub server knows what a good PR review prompt should include. A database server knows what context helps explain schema. A docs server knows how to frame "explain this API" well.

So, prompts are like reusable recipe cards -

    When the user wants to do this kind of task, here is the best instruction format to start from

It does not cook the meal. It gives the model the recipe.

# AN AI APP CAN USE MULTIPLE MCP SERVERS AT A TIME

The real power of MCP is when multiple servers work together.

For example, we might say -

    Find the bug from the logs, patch the repo, open a PR, and message the team.

So, this might include reading production logs using the logging MCP server, inspecting source files using filesystem MCP server, checking issues using GitHub MCP server, running database queries using database MCP server, creating pull requests using GitHub MCP server and notifying team using Slack MCP server.

From the user’s point of view, it feels like one assistant doing a workflow. Under the hood, the host is calling different MCP servers.

The coordination mostly happens in the model/host loop:

    1. Model decides it needs logs.
    2. Host calls logging server.
    3. Model reads result.
    4. Model decides it needs source files.
    5. Host calls filesystem server.
    6. Model decides it needs GitHub issue context.
    7. Host calls GitHub server.
    8. Model produces final answer or calls another tool.

So MCP is composable because all servers expose capabilities in a common shape:

    tools/list
    tools/call
    resources/list
    resources/read
    prompts/list
    prompts/get

Another example is if we have three MCP servers -

    filesystem server
    database server
    GitHub server

And we ask the AI app -

    Check if the signup bug is related to yesterday’s database migration and prepare a fix.

The model may do -

    database server:
    read migration history / query schema

    filesystem server:
    read backend signup code

    GitHub server:
    search recent issues / PRs

    filesystem server:
    edit code

    GitHub server:
    create PR

Remember, the servers are not collaborating with each other directly. They are collaborating through the AI app.

An MCP server is generally a provider of capabilities, not an orchestrator of other MCP servers. A custom server could call another MCP server internally, but that is not the normal mental model. The clean architecture is -

    MCP client is the coordinator.
    MCP servers are specialized adapters.
